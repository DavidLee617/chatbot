### T3 查询翻译

| 现象 | 原因 | 解决 | 结果 |
|---|---|---|---|
| 中文提问的 recall@1 比英文低 18 个百分点 | 书是英文的，中文问题和英文原文跨语言比相似度效果差 | 把问题翻译成英文，和原问题各检索一次，按块去重、取较高分 | recall@1 从 75.0% 升到 96.4%，并且两次运行结果完全一致 |

### T5 Rerank

| 现象 | 原因 | 解决 | 结果 |
|---|---|---|---|
| 在翻译方案上加 rerank，recall@1 从 96.4% 降到 78.6% | 逐题看是真的排错：rerank 偏爱译者导言这类综述性段落 | **默认关闭**，代码保留 | 每题省下约 6,900 tokens 和 2 秒以上 |
| 开了 rerank 后，排第 1 的块不一定是相似度最高的 | 评估判断拒答时只看第 1 名，和线上逻辑不一致 | 统一成"有任何一块过阈值就回答" | 不开 rerank 时结果完全不变 |
| **Web 模式起不来**（T7 时才发现） | WebFlux 应用里 Spring Boot 不自动配置 `RestClient.Builder`，`Reranker` 注入失败；评估走的是 CLI 模式，所以一直没暴露 | 自己定义一个带超时的 `RestClient.Builder` bean | 两种模式都能启动，HTTP 超时也真正生效了 |

**教训**：rerank 不是"加上就变好"，召回已经很高时它可能把精度拉低。另外，改了 bean 或依赖之后，CLI 和 Web 两种模式都要启动一次。

## 三、评价指标：含义、怎么排查、怎么改

RAG 问答系统可以按流水线分层评估，每一层有自己的指标。某个指标差的时候，**先定位是哪一层的问题**，再选改法。

```
问题 → 路由（危机 / 拒答 / 反问）→ 改写 / 翻译 → 检索 → 排序 → 上下文组装 → 生成 → 回答
         ↑路由准确率                    ↑召回率      ↑排序质量    ↑预算          ↑忠实度、相关性
```

### 1. 召回率（recall@k）：正确的段落有没有被找回来

**含义**：有答案的题里，前 k 块中至少有一块正确的比例。它是 RAG 的上限：没找回来的，模型不可能答对。

**不够时按顺序排查**：

1. **是不是评估判错了？** 逐题看取回的块是否其实是对的，只是证据短语没写全。
   - 例：T1 的 a01、T2 的 f02。
   - 改法：修标注，并在变更记录里写明原因。
2. **正确的段落在库里吗？** 检查清洗和切块：内容有没有被删掉、有没有被切碎。
   - 例：T0 的下划线残留、目录和书尾索引的处理。
3. **索引有没有漏检？** 用暴力计算（逐块算余弦）和向量库的结果对照。
   - 例：T3 的 HNSW `ef`。改法：调大 `ef` 或 `nprobe`。
4. **问题和原文的说法不一样？**
   - **跨语言**：翻译查询（T3，本项目收益最大）。
   - **口语和术语不一致**：查询改写，或者多改写几个版本再合并（multi-query）。
   - **专有名词、精确术语**：加 BM25 全文检索，和向量检索做混合检索（本项目没做，只作为面试话术）。
   - **问题太短、太抽象**：HyDE，先让模型写一段假想答案，再用它去检索。
5. **多轮里的指代**：结合历史改写（T4、T6）；新对话里结合记忆解析（T9）。
6. **k 太小**：加大 k，或者先粗召回更多块，再精排。

**本项目的数字**：中文 recall@5 从 92.9% 升到 100%（T3），多轮追问从 42.9% 升到 85.7%（T4 + T6）。

### 2. 排序质量（recall@1、MRR）：正确的段落排得够不够靠前

**含义**：
- recall@1 是排在第 1 名的就是正确段落的比例。
- MRR 是第一个正确段落名次倒数的平均值：排第 1 得 1 分，排第 3 得 1/3 分。
- 模型最看重前几块，预算紧时后面的块还会被裁掉，所以排序决定了回答的质量。

**recall@k 高、recall@1 低时，可以这样改**：
- **合并多路检索结果**：本项目把原问题和译文两路结果合并，取较高分（T3，recall@1 从 75% 升到 96.4%）。也可以用 RRF 这类按名次融合的方法。
- **Rerank**：用 cross-encoder 精排。**要用数据决定开不开**，本项目的实测是开了反而变差（T5）。
- **块之间去重**：相邻块因为有重叠，内容会重复，会占掉 top-k 的名额。可以按 chunkIndex 去重。
- **元数据过滤或降权**：比如把译者导言（Front Matter）降权，问题里点名了作者时只检索那位作者的书。
- **调整切块大小**：块太大，主题会被稀释；块太小，上下文不够。改了要重新导入、重跑评估。

### 3. 拒答正确率和误拒率：该拒的拒了吗，不该拒的有没有被拒

**含义**：
- **拒答正确率**：知识库里没有答案的题，被正确拒答的比例。本项目是 5/6。
- **误拒率**：有答案的题，因为分数低于阈值被拒答的比例。评估里叫"阈值后召回"，它和 recall@k 之间的差距就是被阈值误杀的部分。

**怎么改**：
- **阈值扫描**：每个阈值下，算出误拒几道、放过几道，再按产品偏好选一个点。
- **单一阈值挡不住"看起来相关"的问题**（n06《红书》得 0.51，比好几道有答案的题还高）。这时要靠生成阶段兜底：提示词要求"资料不足就直说"。另一个办法是加一个意图或范围分类器。
- **提高召回也能减少误拒**：正确段落的分数上去了，自然就过了阈值（T3 之后，有答案的题最低分从 0.459 升到 0.499）。

### 4. 危机识别：识别率、误报率、安全余量

**含义**：
- **识别率**：危机里认出来的比例。漏判的代价最大，所以评估集里的危机题必须保持 100%。
- **误报率**：理论题、日常倾诉被误判成危机的比例。误报会让用户觉得被冒犯，也会让真正的提示失去作用。
- **安全余量**：阈值的可用区间有多宽，最险的那道题两个分数相差多少。区间越窄，换一种说法越容易漏。

**怎么改**：
- **漏判**：
  - 补强关键词（第一人称意图）。
  - 补危机例句（注意不能和测试题撞车）。
  - 加一层模型判定（T7）。
  - 判过危机后保持警觉一段时间（followUp）。
- **误报**：
  - 加反例类别，比如理论讨论（T2）。
  - 让模型理解"谈论这个话题"和"本人有这个意图"的区别（T7）。
- **不要用"降低门槛"来提高识别率**。T7 试过，一次误报会连锁锁住整段对话。
- **多轮场景**要用专门的多轮题测。单轮评估测不到上下文里的风险信号。

**本项目的数字**：单轮 1/8 → 8/8；多轮危机轮 13/15 → 15/15，误报 4/43 → 0/43。

### 5. 生成质量：忠实度、引用正确率、答案相关性

本项目只做过一次人工核对（T0），**这是目前最大的空白**。

| 指标 | 含义 | 本项目 | 怎么测 | 不够时怎么改 |
|---|---|---|---|---|
| 忠实度（有没有编造） | 回答里的每个论断，资料里都找得到依据 | 编造 0 处（31 处引用） | 人工抽查；或者让另一个模型逐句判断有没有依据（RAGAS faithfulness 这一类） | 提示词里强调"只根据资料"；降低 temperature；资料不足时要求直说 |
| 引用正确率 | [n] 指向的块确实支持那句话 | 30/31 | 人工核对，或者自动比对引用句和对应块 | 要求每句只引一个来源；后处理检查编号是否存在 |
| 答案相关性 | 回答是不是在回答用户问的那个问题 | Q1 答非所问（检索错了） | 人工打分；或者让模型判断回答是否覆盖了问题 | 通常是检索问题，先修检索 |
| 上下文精确率 | 放进 prompt 的块里，有用的占多少 | 没测 | 让模型判断每块和问题是否相关 | rerank、去重、减小 k、上下文预算 |
| 偏好遵守 | 记忆里的偏好（比如"简短"）有没有生效 | 端到端看过一次（回答 3 句话） | 跨对话剧本 + 检查回答长度、格式 | 调整记忆在 prompt 里的位置和措辞 |

**建议的下一步**：抽 20 道题做生成评估。用另一个模型当评委，打忠实度、相关性两项分，每次改提示词或检索后都跑一遍，同时人工复核评委的判断。

### 6. 多轮与记忆的指标

| 指标 | 含义 | 本项目 | 不够时怎么改 |

### 7. 成本、延迟、稳定性

这些指标不直接衡量"答得对不对"，但决定系统能不能上线。

| 指标 | 本项目现状 | 怎么改 |
|---|---|---|
| 首字延迟（用户要等多久） | 翻译或改写约 1.5 s + 检索；危机判定调用 LLM 的轮次再加约 1.3 s | 翻译和危机判定并行；换更快的模型；缓存常见问题的译文 |
| 每题 token 数 | 翻译约 200；记忆提炼约 500（在后台）；rerank 约 6,900（所以没开） | 只在需要时调用（危机判定有粗筛，只有 2/34 道普通题会触发） |
| 每题模型调用次数 | 普通题 2 次（翻译 + 生成），加 1 次后台记忆提炼 | 合并调用（翻译和改写、指代解析都合成了一次） |
| 结果稳定性 | 检索评估是确定性的；只用译文的方案不稳定；记忆提炼不稳定 | 多路结果合并兜底（T3）；关键规则在代码里兜底（T9）；每个结论至少跑两次 |
| 降级 | 翻译失败 → 用原问题检索；危机判定失败 → 退回语义规则；数据库不可用 → 不用记忆 | 每个外部调用都要有退路，并且记日志 |
| token 估算误差 | 比实际高 15–35% | 用日志里的实际值校准；或者接入真正的 tokenizer |

### 8. 评估本身的质量

这一节说的是怎样保证上面这些数字可信。

- **冻结题库**：调参之前先冻结题目。要改题必须写明原因，并保留改动前后两次的结果（`eval/README.md` 的变更记录）。
- **留出集**：改提示词之前先写好题、提交固定。本项目 T6、T8、T9 都这样做了。
- **区分"评估判错"和"真的错了"**：逐题看结果，不只看汇总数字（T1、T5）。
- **要有精确检索的对照**：用暴力计算对照向量库，排除索引漏检（T3）。
- **复现性**：同一配置至少跑两次。检索是确定性的；凡是涉及模型调用的环节，都要跑多次看稳定性（T9 的 u08 就是这样发现的）。
- **样本量**：相差 1–2 道题的变化不下结论；阈值的可用区间很窄时，明确写"不是稳的结论"。
- **看了结果才做的调整要如实记录**（T7 的自我认同规则、T8 的召回阈值），这些题之后不能再算作留出证据。
